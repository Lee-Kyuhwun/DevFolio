# Dev Team: 사용자 데이터와 문서 결과의 신뢰성 점검

2026-10-24. 사용자 요청: 프로젝트의 사용자 관점 문제를 찾고 개선한 뒤 LLM Wiki에 기록한다. `ecc:dev-team`과 `ecc:java-coding-standards`를 사용했다. Java 빌드 파일은 없으므로 Python에 맞는 명확성·검증·타입·도메인 예외 원칙을 참고했다.

## 프로젝트 맥락

DevFolio는 Python 3.11+ 기반 로컬 우선 포트폴리오 CLI와 웹 스튜디오다. Typer, Pydantic v2, ruamel.yaml, Jinja2를 사용하며 FastAPI·AI·문서 출력은 선택 기능이다. 기존 제품을 개선하는 단계이며, 사용자 데이터 보존과 회귀 검증이 완료 기준이다. `PROJECT-CONTEXT.md`는 없었다. 기존 `AGENTS.md`로 점검했으며 개요 파일 생성은 별도 승인 전에는 하지 않았다.

## PM

**첫 반응:** 사용자는 정리한 경력과 제출 문서를 신뢰할 수 있어야 한다. 데이터가 바뀌는 작업과 실패 후 복구 가능성을 우선 확인한다.

**핵심 우려:**

- 비슷한 이름을 가진 프로젝트를 수정하거나 삭제할 때 대상이 정확해야 한다.
- 성공 안내는 실제로 저장되거나 복원된 상태와 일치해야 한다.
- 한 번의 점검으로 모든 기능을 재설계하기보다, 피해가 큰 재현 가능한 결함부터 해결한다.

**첫 행동:** 조회·수정·삭제·가져오기·복원에서 원본 보존을 수용 기준으로 정한다.

**팀 질문:** 제출 문서를 만들기 전에 사용자가 무엇을 검토하고 확인할 수 있어야 하는가?

## Architect

**첫 반응:** CLI와 웹이 같은 파일을 다루므로 저장 일관성과 실패 후 복구가 신뢰의 핵심이다. 다음 항목은 코드 점검 전 위험 가설이다.

**핵심 우려:**

- 저장 실패 시 원본 바이트 보존, 정상 저장 시 원자적 교체, 동시 편집 충돌 처리.
- 미리보기의 비변경성, 선택한 초안과 출력의 일치, 출력 실패 시 기존 파일 보존.
- 초기화 누락·손상 데이터·선택 의존성 누락에 대한 조치 가능한 안내.

**첫 행동:** 임시 저장소에서 입력→검증→저장→출력 경로에 실패를 주입한다.

**팀 질문:** CLI와 웹의 동시 수정 충돌을 어디에서 책임지는가?

## Developer

**첫 반응:** 입력한 경력과 저장·미리보기·내보내기 결과가 일치하는지가 핵심이다. 다음 항목은 검증할 위험 가설이다.

**핵심 우려:**

- 잘못된 날짜나 쓰기 실패가 원본과 작성 중 입력을 손상시키는지 확인한다.
- 오래된 비동기 응답이 최신 편집을 덮는지, 출력이 선택한 데이터를 쓰는지 확인한다.
- 복원·출력의 부분 실패가 성공으로 표시되지 않아야 한다.

**첫 행동:** 정상 흐름을 임시 저장소에서 실행한 뒤 잘못된 날짜·쓰기 실패·손상 백업을 주입한다.

**팀 질문:** 내보내기는 현재 화면과 마지막 저장본 중 무엇을 사용하는가?

## QA

**첫 반응:** 작성한 경력이 사라지거나 성공 안내와 결과가 다르면 사용자 피해가 크다. 다음 항목은 재현 전 우선 점검 시나리오다.

**핵심 우려:**

- 손상 YAML·스키마 오류·복원 중 쓰기 실패에서 원본이 유지되어야 한다.
- 공백 이름·역전 기간·없는 ID·저장 실패를 확인하고 실패에 성공 안내를 내지 않는다.
- HTML 특수문자·경로 이동·선택 의존성 누락과 잘못된 출력 경로를 확인한다.

**첫 행동:** 최초 실행부터 CRUD·미리보기·백업·복구까지 연결하고, 보호 조치를 제거하면 테스트가 실패하는지 확인한다.

**팀 질문:** 앱 종료나 저장 실패 후 어느 시점까지 복구할 수 있는가?

## Synthesis

네 관점이 공통으로 제기한 **데이터 손실·실패를 성공으로 표시하는 문제는 출시를 막아야 할 항목**으로 판단했다. 가설을 결함으로 단정하지 않고 임시 데이터로 재현한 뒤 수정했다.

- PM의 제한된 범위와 QA의 넓은 실패 조합 사이에는 긴장이 있다. 이번에는 조회/import, 저장, 복원, 입력, HTML, 출력 경로의 여섯 범주를 고쳤다.
- 설계 관점의 동시 편집 충돌은 파일 원자적 교체만으로 해결되지 않는다. 충돌 감지는 후속 검토 항목으로 남겼다.
- 생성·심사 품질이나 provider 실환경은 별개 검증이므로 이번에는 유료 AI 호출을 하지 않았다.
- 결과는 `docs/agent-incidents.md` INC-13~18과 `test_inc13_*`~`test_inc18_*`로 연결했다. 세부 근거는 LLM Wiki의 2026-10-24 사용자 관점 점검 페이지에 기록한다.

## 검증

기존 252개 → 최종 285개 테스트 통과. `make check`에서 ruff·포맷·pytest를 확인했다. 여섯 범주의 구현을 각각 이전 코드로 되돌린 임시 복사본에서는 선택한 회귀 테스트가 모두 실패했고, 현재 구현에서는 새 테스트 33개가 통과했다.
