# AI 심사 신뢰도 측정 — 설계

- 상태: 설계 검토 중
- 작성: 2026-10-03
- 선행: [문장별 근거 검사와 사람 승인](2026-10-03-claim-grounding-review-design.md)의 검사기(`claim_check`)

## 1. 배경

DevFolio는 생성 결과를 심사 모델이 7축으로 채점하고, 그 점수로 후보를 고르고 통과 여부를 정한다.
그런데 이 채점이 사람의 판단과 얼마나 일치하는지 잰 적이 없다.
"어느 판단을 AI에 맡기고 어느 판단을 사람이 해야 하는가"를 감이 아니라 측정으로 정하는 것이 이 작업의 목적이다.

## 2. 측정 질문

- **Q1.** 심사 모델의 판정은 사람의 판정과 항목별로 얼마나 일치하는가?
- **Q2.** 근거 없는 사실을 심사 모델은 얼마나 놓치는가? 결정적 검사기는 얼마나 잡고, 얼마나 오탐하는가?
- **Q3.** 생성 전략 4종(single, best_of_n, s1_refine, hybrid)의 품질과 비용은 어떻게 다른가?

## 3. 사전에 정한 판정 규칙

결과를 본 뒤 기준을 결과에 맞추는 일을 막으려고, 데이터를 보기 전에 규칙을 고정한다.

| 조건 | 결정 |
|---|---|
| 사람 판정과의 일치율 80% 이상인 항목 | 심사 모델 자동 판정 유지 |
| 일치율 80% 미만인 항목 | 사람 검토 필수 항목으로 지정하고 검토 화면에 표시 |
| 근거 없는 사실이 있는 출력 중 심사 모델이 놓친 비율이 10% 초과 | 근거 확인을 사람 필수 단계로 고정 (근거 검사 + 사람 확인) |

## 4. 데이터

- **사례**: 본인의 실제 프로젝트 5개를 evidence YAML로 작성한다.
  - 회사 프로젝트 정보가 들어가므로 저장소에 커밋하지 않는다(`evals/cases/`는 gitignore).
  - 공개용으로는 익명 예시 1개만 커밋한다(`evals/examples/sample_case.yaml`).
- **모드**: `project_summary` 하나. 근거 검사 설계와 같은 모드다.
- **규모**: 5개 사례 × 4개 전략 = 출력 20개
  - 소규모 파일럿이다. 보고서에 표본 크기와 한계를 명시한다.
- **전략 설정**: best_of_n과 hybrid는 `samples=3`으로 고정한다.
  - 샘플이 2개 미만이면 `_resolve_reasoning_plan`이 전략을 single로 바꿔 비교가 무의미해진다.
  - s1_refine은 refine 예산을 1 이상으로 둔다.
  - 실제로 적용된 전략과 설정값(`ReasoningPlan`)을 출력마다 기록해, 의도한 전략이 실행됐는지 확인한다.
- **비용**:
  - 기본 provider는 pollinations(무료)
  - 실행 전에 예상 호출 수를 출력하고 확인을 받는다(`CLAUDE.md`의 AI API 호출 확인 규칙).

## 5. 사람 라벨링

- **블라인드**: 라벨링 화면에서 심사 점수와 전략명을 숨기고 순서를 섞는다.
- **항목**: 7축 전체를 사람이 채점하면 부담이 커서 3개로 줄인다.

| 사람 라벨 | 비교 대상 |
|---|---|
| 근거 없는 사실 있음/없음 + 해당 표현 | 심사 모델 `factuality` (3 미만이면 "있음"으로 간주), 결정적 검사기 결과 |
| 자연스러움 1~5 | 심사 모델 `naturalness` (둘 다 4 이상인지로 일치 판정) |
| 그대로 사용 / 수정 필요 / 사용 불가 | 심사 모델 `pass` ("그대로 사용"이면 통과로 간주) |

## 6. 구성 요소

개발용 도구이므로 `devfolio` CLI에 노출하지 않고 `evals/` 스크립트로 둔다.

| 파일 | 역할 | 출력 |
|---|---|---|
| `evals/run.py` | 사례 × 전략 생성 실행. `AIService` 하위 클래스로 호출 수와 지연 시간을 센다 | `evals/runs/<run_id>/outputs.jsonl`<br>필드: 사례, 전략, 텍스트, 심사 점수, 통과 여부, 근거 검사 결과, 호출 수, 지연 시간 |
| `evals/label.py` | 터미널에서 블라인드 라벨링 | `labels.jsonl` |
| `evals/report.py` | 통계 계산과 판정 규칙 적용 | `report.md` |

- `report.md`에 담는 내용:
  - 항목별 일치율, 이진 판정의 Cohen's kappa
  - 심사 모델이 놓친 비율
  - 검사기의 재현율과 오탐률
  - 전략별 표, 판정 규칙 적용 결과
- `evals/runs/`는 원문이 들어가므로 gitignore한다. 공개해도 되는 요약 수치만 `docs/`로 옮긴다.

## 7. 테스트

- `report.py` 계산 함수(일치율, kappa, 놓친 비율)를 합성 라벨로 단위 테스트한다.
- `run.py`는 모킹한 AI로 스모크 테스트한다. 실제 API는 호출하지 않는다.

## 8. 역할 분담

| 일 | 담당 |
|---|---|
| 측정 질문과 판정 규칙을 사전에 정함 | 사람 |
| evidence 작성 (사실의 원천) | 사람 |
| 블라인드 라벨링 | 사람 |
| 결과 해석과 반영 결정 | 사람 |
| 측정 도구 구현, 생성·채점 실행 | AI |
| 통계 계산 | 코드 |

## 9. 결과 반영

판정 규칙에 따라 "사람 검토 필수"로 지정된 항목은 근거 검사 설계의 검토 화면에 표시하고 `docs/ai-collaboration.md`의 역할 분담 표에 반영한다.

## 10. 성공 기준

- 출력 20개를 모두 라벨링하고 보고서를 만든다.
- 판정 규칙에 따라 항목별 "자동 / 사람 필수"가 결정되고, 그 결과가 화면과 문서에 반영된다.

## 11. 실측 후 기록할 값

추정치는 쓰지 않고, 실제 실행한 값만 기록한다.

- 항목별 일치율과 kappa
- 심사 모델이 놓친 근거 없는 사실의 비율
- 결정적 검사기의 재현율과 오탐률
- 전략별 평균 호출 수와 지연 시간
