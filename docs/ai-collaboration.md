# DevFolio의 AI 협업 방식

DevFolio는 코딩 에이전트(Claude Code, Codex)와 함께 개발했다.
이 문서는 사람과 AI가 각각 무엇을 맡았는지, 사람의 역할을 왜 그렇게 정했는지, 그 결정의 근거(커밋, 테스트, 측정)를 기록한다.

## 두 개의 Loop

```
[개발 Loop]
사람: 범위·규칙 결정 ──▶ 에이전트: 구현 ──▶ 자동 검증(scripts/check.sh) ──▶ 사람: 실제 모델로 실행
      ▲                                                                    │
      └──── 장애 기록(agent-incidents.md) + 회귀 테스트 ◀──────────────────────┘

[제품 Loop]
evidence ──▶ 생성 모델: 초안 ──▶ 심사 모델: 7축 채점 ──▶ 코드 재검증(통과 기준)
         ──▶ 결정적 근거 검사 [예정] ──▶ 사람: 문장별 채택 [예정]
                ▲                                                          │
                └──── refine 피드백 (점수 미달 / 근거 없는 표현 [예정]) ◀───────┘
```

> [예정] 표시는 설계와 구현 계획까지만 있고 아직 구현하지 않은 부분이다(2026-10-03 기준).
> 장애 기록부와 회귀 테스트는 2026-10-03에 구현했다(`docs/agent-incidents.md`, `tests/test_incident_regressions.py`).
> 지금은 웹에서 생성한 요약이 사람 확인 없이 바로 저장된다.

## 역할 분담

### 개발 Loop

| 단계 | 사람 | AI | 근거 |
|---|---|---|---|
| 범위·우선순위 결정 | 결정 | 선택지와 근거 제시 | 이 문서, 설계 문서 |
| 규칙 정의 | 금지 목록 작성 (`AGENTS.md`) | 규칙을 따름 | `AGENTS.md` |
| 구현 | 검토 | 구현 (병렬 worktree) | 커밋 이력 |
| 자동 검증 | 통과 기준 정의 | 매 커밋 실행 | `scripts/check.sh` |
| 실서비스 장애 발견 | 실제 provider에서 드러난 실패 (발견 경위 확인 필요) | 수정 | fix 커밋, `docs/agent-incidents.md`, `test_incNN_*` 회귀 테스트 |
| AI 분석의 교차 검증 | 다른 AI의 분석을 그대로 쓰지 않고 검증을 요구 | 저장소를 직접 확인해 주장별로 판정 | 아래 2026-10-03 기록 |
| 검증 장치 자체의 검증 | 실험 계획 승인 | 일부러 깨뜨린 변경으로 실험을 제안·수행 | 아래 2026-10-03 기록 |

### 제품 Loop

| 단계 | 사람 | AI / 코드 |
|---|---|---|
| 사실의 원천 (evidence) | 작성 | — |
| 초안 생성 | — | 생성 모델 |
| 품질 채점 | 7축 기준과 가중치 결정 | 심사 모델 |
| 채점 결과 재검증 | 통과 기준 결정 (모든 축 3점, naturalness 4점) | 코드 (`ReviewResult`) |
| 근거 검사 [예정] | 무엇을 사실 주장으로 볼지 결정 | 결정적 코드 |
| 최종 채택 [예정] | 문장별 승인·수정·삭제 | — |

## 사람이 맡는 판단과 그 이유

AI가 스스로 통과시킬 수 있는 것은 테스트, 린트, 자기 채점까지다.
다음 세 가지는 그 범위 밖에 있어서 사람이 맡는다.

1. **실제 외부 서비스에서만 드러나는 실패**
   무료 등급 quota 0, 지원 종료 모델 404, 빈 응답, 언어 지시를 무시한 외국 문자 혼입은 모킹된 테스트에서는 재현되지 않았고, 실제 provider 응답에서 드러났다(fix 커밋 메시지 기준). 누가 어떤 경로로 발견했는지는 확인 필요.
   2026-10-03에는 이 사실이 다시 확인됐다. 테스트 242개와 CI가 모두 통과한 상태에서, 사람이 "실제로 AI를 호출해 테스트해볼 수 있나"를 요청했다. 그 첫 실행에서만 장애 3건(INC-09~11)이 연달아 드러났다(아래 기록).
2. **생성 결과의 사실 여부**
   evidence 밖의 사실을 판정하는 심사 모델도 생성 모델과 같은 착각을 할 수 있다. 사실의 원천을 아는 사람이 최종 판단한다. 이 판단을 얼마나 AI에 맡길 수 있는지는 측정으로 정한다(심사 신뢰도 측정 설계 참고).
3. **검증 장치가 실제로 작동하는지**
   설정 파일이 있다는 것과 실제로 막는다는 것은 다르다. 2026-10-03 점검에서 확인했다.

## 2026-10-03 검증 장치 복구 기록

### 발견한 상태

| 장치 | 설정상 | 실제 |
|---|---|---|
| GitHub Actions CI | push마다 lint + 테스트 | 76회 실행 모두 실패, 방치됨. 원인은 ruff 오류 27건, 포맷 미적용 38개 파일 |
| pre-commit | ruff 설정 파일 존재 | `pre-commit install`을 하지 않아 실행된 적 없음 |
| Claude Code 커밋 훅 | 커밋 전 pytest | 테스트 실패(종료 코드 1)는 막지 않음. 차단은 종료 코드 2일 때만 |
| main 브랜치 | — | `ai_service.py` 문법 오류로 테스트 3개 파일 수집 불가 |

스마트 따옴표가 들어간 커밋은 테스트 수집 오류(pytest 종료 코드 2)를 냈을 것이다. 그래서 Claude Code 훅을 거치지 않은 경로로 커밋된 것으로 보인다.
이 때문에 검증을 특정 에이전트 설정이 아니라 git 훅과 CI에 두기로 했다.

### 조치

- `76bb520`: 문법 오류 수정, ruff 0.15.11 고정과 포맷 적용, 심사 통과 기준을 코드로 강제
- `2452b7a`:
  - `scripts/check.sh`(ruff + 포맷 검사 + pytest -x)를 git pre-commit 훅과 Claude Code 훅이 함께 사용
  - Claude Code 훅은 실패하면 종료 코드 2로 차단

### 막히는지 실험한 결과 (push 전)

| 실험 | 결과 |
|---|---|
| A. 실패하는 테스트 커밋 | pre-commit이 차단, HEAD 변화 없음 |
| B. 스마트 따옴표 문법 오류 커밋 | ruff가 차단, HEAD 변화 없음 |
| C. `git commit --no-verify` (Claude Code 훅 경유) | 종료 코드 2로 차단 |
| D. 커밋이 아닌 명령 | 통과 (종료 코드 0) |
| E. 정상 상태에서 커밋 | 통과 (종료 코드 0) |

push 후 CI run `37106604049`에서 lint와 Python 3.11 / 3.12 / 3.13 테스트가 모두 성공했다. 처음으로 통과한 CI다.

역할 (2026-10-03 대화 기록 기준):

| 사람 | Claude Code |
|---|---|
| 과제 준비 중 다른 AI가 만든 저장소 분석을 그대로 쓰지 않고, 주장별 검증을 요구 | 저장소·CI·로그를 직접 확인해 주장별로 판정, CI 실패와 문법 오류 발견 |
| "지금 상태로 쓰지 말고 개선한 뒤 쓰겠다"고 결정 | 개선안 제시 |
| 범위 선택과 각 단계 승인 | 검증 장치 설계, 구현, 차단 실험 A~E 제안·수행, push |

검증을 git 훅·CI에 두는 방식, 차단 실험, 심사 신뢰도 판정 기준(80%, 10%)은 Claude Code가 제안하고 사람이 승인했다.

## 2026-10-03 오후 첫 실제 실행 기록

심사 신뢰도 측정 도구(`evals/`)를 모킹 테스트로 완성한 뒤, 사람이 "실제로 AI를 호출해 결과를 테스트해볼 수 있나"를 요청했다.

| 순서 | 일어난 일 | 결과 |
|---|---|---|
| 1 | pollinations로 가상 사례 1건 실행 | **INC-09**: 무료 등급이 긴 요청에 HTTP 200으로 "크레딧 부족" 문장을 돌려줬고, DevFolio가 이를 요약 초안으로 받아들임 → 수정 |
| 2 | 사람이 무료 API 후보 조사를 요청, Gemini 키 등록 | 측정 실행기가 실패 시 내장 pollinations로 넘어가는 것을 발견 → 고른 provider로만 전송하도록 수정 |
| 3 | 키가 등록 직후 사라짐 | **INC-10**: 테스트가 실제 macOS 키체인에 `test-key`를 써서 등록한 키를 덮어씀. 커밋마다 pre-commit이 테스트를 돌리면서 반복됐다 → 테스트 격리, 키 재등록 |
| 4 | 등록 모델(gemini-2.5-flash)이 신규 사용자에게 404 | 측정에서만 모델을 고정하고(`--model`), 모델이 조용히 바뀌지 않게 함 |
| 5 | 심사 응답이 110자에서 잘림 | **INC-11**: 추론 모델의 생각 토큰이 출력 한도를 소모 → 한도 상향, 같은 사례로 재실행해 정상 확인 |

| 사람 | Claude Code |
|---|---|
| 모킹 테스트 통과에서 멈추지 않고 실제 실행을 요구 | 실행, 원인 분석(로그·curl 재현·키체인 수정 시각 비교), 수정, 회귀 테스트 |
| 전송 범위 결정: 회사명을 가린 사례만, 고른 provider로만 | 가린 사례 작성, 전송 대상 강제와 실행 전 표시 |
| 무료 API 조사 요청, Gemini 키 발급·등록·재등록 | 무료 등급 한도 조사와 비교, 키 값은 보지 않고 형식·인증만 진단 |

같은 날 Claude Code의 커밋도 `scripts/check.sh` 훅에 두 번 막혔다(포맷 미적용 테스트 파일). 검증 장치는 에이전트에게도 동일하게 작동한다.

## 2026-10-03 심사 신뢰도 측정 결과 (파일럿)

- 설정: 가린 실제 사례 5개 × 전략 4종 = 출력 20개. 생성·심사 모두 NVIDIA NIM `openai/gpt-oss-20b`(무료 등급). 사람은 "evidence에 없는 사실이 있는가"만 블라인드로 판정했다.
- 판정 규칙은 데이터를 보기 전에 정했다(일치율 80%, 놓친 비율 10%).

| 항목 | 결과 |
|---|---|
| 사람 판정 | 근거 없는 사실 0건 / 20건 (정정 후) |
| 심사 모델 | factuality 20건 모두 5점 |
| 일치율 | 100%, kappa 계산 불가(모두 같은 값) |
| 심사 모델이 놓친 비율 | 계산 불가(사람이 찾은 사례 없음) |
| 사전 규칙 판정 | factuality auto. 단 **반대 증거가 없다는 뜻일 뿐, 심사 모델이 근거 없는 사실을 잡는지는 측정되지 않았다** |

전략별 비용(심사 모델 기준, 사람 사용 가능 여부는 미측정):

| 전략 | 평균 호출 | 평균 시간 | 심사 통과율 |
|---|---|---|---|
| single | 2.0 | 31초 | 0% |
| best_of_n | 6.0 | 124초 | 0% |
| s1_refine | 6.0 | 165초 | 20% |
| hybrid | 11.6 | 300초 | 60% |

best_of_n·hybrid는 심사 모델이 고른 후보라 통과율이 치우칠 수 있다.

### 측정 과정에서 드러난 오류 (사람·규칙·AI 모두)

| 누구의 오류 | 무엇 | 어떻게 드러났나 | 처리 |
|---|---|---|---|
| 사람 | 1차 채점: 빨리 넘기느라 20건 중 19건이 같은 답 | 라벨 분포 확인 후 본인이 인정 | 폐기·보관, 질문을 명확히 하고 "같은 답 반복" 경고 추가 |
| 결정적 규칙 | 2차 채점 후 점검: 20건 중 11건을 후보로 표시(연도 표기, API·REST 같은 일반 용어 등 오탐 다수) | 사람이 11건을 다시 확인 | 정밀도가 낮음 → 근거 검사기(★1) 설계에 반영할 점 |
| 사람 | 3차: "10 %"를 "1%"로 오독 | 생성문과 evidence 대조 | 본인 결정으로 정정, 사유 기록 |
| 사람(입력) | 팀 인원을 모르는 채 넣은 자리표시(1)를 생성 모델이 그대로 "1인 팀"으로 씀 | 사람이 "실제는 4명"이라고 표시 | evidence 오류로 분류. 사실의 원천(evidence)이 틀리면 생성·심사 모두 틀린 것을 맞다고 본다 |

정리: 이 표본에서는 **AI 심사가 틀린 사례가 확인되지 않았고, 오류는 오히려 사람의 채점과 사람이 만든 evidence, 단순 규칙에서 나왔다.** 사람이 최종 판단을 맡는다는 것은 사람이 항상 옳다는 뜻이 아니다. 그래서 사람의 판정에도 일관성 검사와 대조가 필요하다.
