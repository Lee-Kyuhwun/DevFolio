# ImpactNote 환각 근본 원인 분석

작성일: 2026-11-16 · 조사 대상: `impactnote/core/ai.py`, `metrics.py`, `claims.py`,
`intel/ai_stage.py`, `report.py`, `service.py`, `evals/impact/`
기준 데이터: `impactnote-ai-eval-1.0.0` (42 claims, 동결)

> 이 문서는 **2026-10-03 Historical 생성문의 47.6%** 와 **2026-11-16 현재 파이프라인의
> 측정값** 을 구분한다. 과거 수치를 현재 성능으로 읽지 않는다.

## 1. 조사 방법

1. 실패 문장을 입력 → 프롬프트 → 모델 응답 → 저장 → 보고서 순서로 역추적했다.
2. 42개 claim 을 "효과 주장 / 사실 주장 / 수치 주장"으로 분류하고, 각 주장이 어느
   검증 단계를 통과했는지 코드 경로로 확인했다.
3. 2026-11-15에 저장된 Historical 결과(`docs/evaluation-results.md`)와 2026-11-16
   실제 NVIDIA 호출 3건을 비교했다.
4. 코드로 확인되지 않은 가설은 §7에 별도로 남겼다.

재현:

```bash
./.venv/bin/python -m evals.impact.run --offline --no-judge --out /tmp/impact-offline
./.venv/bin/python -m evals.impact.live_ab --out /tmp/impact-live-ab-v2
./.venv/bin/python -m pytest tests/test_claims.py -q
```

## 2. 파이프라인과 실패 지점

```text
Activity(제목·설명·문제·행동·사용자 기록 결과)
  └─ evidence_ids (선택)
       │
       ├─ A. 검색: 활동에 연결된 Evidence 만 사용. 검색·재정렬 없음
       ├─ B. 문맥: 제목/설명/문제/행동/결과 + 근거 excerpt 를 한 프롬프트에 결합
       ├─ C. 해석: 모델이 기록을 요약·일반화
       ├─ D. 생성: 자유 JSON (title/problem/action/result/statements)
       ├─ F. 검증: 숫자+단위만 대조. 정성 효과 주장은 무검증
       ├─ 저장: analysis.result → apply_analysis → Achievement(source=ai)
       └─ G. 보고서: 미확인 AI 성과는 본문 제외. 확인 후에는 재검증 없음
```

핵심 결함은 **F와 G**다. A~D에서 만들어진 효과 주장을 막을 결정론적 단계가 없었고,
사용자가 "확인"하면 보고서가 그대로 실었다.

## 3. 원인별 분석

### A. Source Retrieval Failure — 부분 확인

- 활동에 Evidence 가 없어도 AI 분석은 실행된다. 프롬프트에는 `(연결된 근거 없음)` 이
  들어가고, 모델은 활동 설명만으로 결과를 작성할 수 있다.
- 프로젝트 분석(`intel/ai_stage.py`)은 인용 ID를 검증하지만, 활동 분석(`ai.py`)은
  인용 ID 자체가 없다. 어느 근거 문장이 어느 주장을 뒷받침하는지 구조적으로 알 수 없다.
- 데이터셋에서는 c005(VOC 자동 분류), c024(SSR/CSR), c038(OAuth2)가 "근거에 없는 기능"
  주장이다. 검색 실패라기보다 **검색 결과에 없는 내용을 생성한 D**에 가깝다.

### B. Context Selection Failure — 확인

- 한 프롬프트에 활동 기록과 근거 excerpt 를 모두 넣는다. 관련 없는 근거가 섞여도
  모델이 이를 "관련 근거"로 오해할 수 있다.
- 활동 1건 단위라 chunk/rerank 필요성은 낮지만, 프로젝트 분석은 문서 12개·코드 8개·
  커밋 10개를 상한 없이 요약해 넣는다(16,000자 상한).
- 이번 라운드에서 검색·재정렬을 새로 도입하지 않았다. 근거 부족 문제의 주원인은
  B보다 D/F로 판단했다(§5).

### C. Evidence Interpretation Failure — 부분 확인

- c034("PostgreSQL 사용" vs 코드는 SQLite), c037("rate limit 100 rpm" vs 설정 50 rpm)은
  기록과 반대되는 해석이다. 숫자 대조로 c032·c040은 잡히지만, 의미 반대는 잡지 못한다.
- c019("수동 배포가 가용성에 위험")는 기록에 없는 인과 해석이다. 근거는 "수동 배포와
  휴먼 에러 기록"까지만 말한다.

### D. Generation Hallucination — 주원인

- `result`와 `statements`가 자유 문자열이다. 프롬프트는 "기록에 없으면 비워라"고
  지시하지만 강제력이 없다.
- 42개 중 20개가 unsupported/contradicted다. 이 중 **12개가 정성 효과 주장**이다:
  운영 비용 절감, 생산성 향상, 확장성·유지보수성 향상, 지연 최소화, 부하 분산,
  가용성 위험, 운영비 상승, 확장성 보장, 응답 시간 70% 단축, 커버리지 90%,
  배포 시간 50% 절감, 고가용성.
- 2026-11-16 실제 호출에서도 `self_review`에 "운영 효율성과 안정성을 크게
  향상시켰습니다", `executive`에 "배포 시간을 15분 단축"이 생성됐다. 전자는 근거가
  없고, 후자는 기록에 없는 수치다.

### E. Attribution Failure — 제한적 확인

- `contribution.role`은 모델이 쓴 자유 문자열이며, Git 작성자·공동 작업과 자동 대조하지
  않는다.
- 통제 저장소 8개 단위의 귀속 exact accuracy는 100%였지만, 이는 커밋 author 기반
  결정론 엔진의 결과다. AI가 쓴 `contribution` 문장의 정확도를 측정한 값이 아니다.
- c001은 팀 규모 4인데 "1인 팀"이라고 쓴 Historical 사례다.

### F. Validation Failure — 직접 원인

- `metrics.sanitize_claims` 는 숫자+단위만 검사했다. "안정성을 향상시켰다"에는 숫자가
  없으므로 아무 검사도 하지 않았다.
- `sanitize_ai_result` 는 중첩 dict/list 까지 재귀하지만, 수치만 대상이다.
- `intel/ai_stage.py` 는 인용 ID와 수치를 검증하지만, 후보의 `result`에 있는 정성
  효과 주장은 검증하지 않았다.
- Judge(독립 심사)는 평가 하네스에만 있고 제품 저장 경로에는 없다.

추가로 2026-11-16 실호출에서 **단위 무시 결함**이 확인됐다. 근거에 `80ms`가 있으면
`80%`라는 파생 수치가 통과했다. 값만 비교하고 단위를 비교하지 않았기 때문이다.
이 결함은 수정했고 `tests/test_claims.py::test_percent_claim_is_not_supported_by_millisecond_value`
로 고정했다.

### G. Reporting Failure — 확인

- `report.build_content` 는 `source in {ai, git, analysis}` 이고 `confirmed=False` 인
  성과를 본문에서 제외한다. 이 부분은 정상이다.
- 그러나 사용자가 확인(`confirmed=True`)하면 `_achievement_lines` 가 `result`를 그대로
  싣고, 수치만 다시 대조했다. 정성 효과 주장은 재검증하지 않았다.
- 즉 **"확인"이 근거 검증을 대체**했다. 확인은 "이 후보를 성과로 쓰겠다"는 뜻이지
  "효과가 입증됐다"는 뜻이 아니다.

## 4. 원인별 발생 비중 (42 claim 기준)

아래 분류는 데이터셋 라벨과 코드 경로를 대조한 **분석자 매핑**이며, 독립 측정값이 아니다.

| 원인 | claim 수 | 예시 |
| --- | ---: | --- |
| D. 생성 — 근거 없는 정성 효과 | 12 | c002, c003, c004, c010, c011, c019, c023, c025, c031, c035, c036, c039 |
| D. 생성 — 근거에 없는 기능 | 3 | c005, c024, c038 |
| F. 검증 — 수치/용량 미검증 | 2 | c032, c040 |
| C. 해석 — 기록과 반대 | 2 | c034, c037 |
| E. 귀속 — 팀 규모/기여 불일치 | 1 | c001 |
| 합계 unsupported/contradicted | 20 | 47.6% |

- 20개 중 12개(60%)가 정성 효과 주장이다. 수치 가드레일만 강화해서는 절반 이상을
  막을 수 없다.
- 나머지 8개는 기능 존재·의미 반대·귀속·용량 주장으로, 별도 검증(인용 근거 대조,
  코드-문서 일치, 기여 귀속)이 필요하다.

## 5. 왜 검색보다 검증이 먼저인가

- 42개 중 12개는 근거가 **이미 문맥에 있는데도** 없는 효과를 생성했다. 검색을 바꿔도
  같은 문장이 나올 수 있다.
- 반대로 정성 효과 Hard Gate 는 22개 효과 주장 중 근거 없는 12개를 전부 차단하고
  근거 있는 10개를 전부 보존했다(§6). 검색 시스템 전체를 도입하지 않고도 측정 가능한
  개선을 만들 수 있었다.
- 검색·재정렬은 c005·c024·c038 같은 "기능 존재" 주장에는 여전히 필요하다. 이번
  라운드에서 해결하지 못한 범위다.

## 6. 현재 파이프라인 측정값 (2026-11-16)

정성 효과 Hard Gate (`impactnote/core/claims.py`) 를 42개 claim 에 적용한 결과:

| 값 | 결과 |
| --- | ---: |
| Gate 적용 대상(효과 주장) | 22 / 42 (52.4%) |
| 근거 있는 효과 claim | 10 |
| 근거 없는 효과 claim | 12 |
| **잘못 통과(false accept)** | **0 / 12** (Wilson 95% CI 0–24.3%) |
| 근거 있는데 차단(false rejection) | 0 / 10 |
| 보존율 | 100% |
| 통과 claim 정밀도 | 100% |

- 0건은 "오류율 0%"를 뜻하지 않는다. 12개 표본에서 0건이면 95% 상한은 24.3%다.
- 이 Gate 는 **효과 주장만** 대상으로 한다. 사실·기능·귀속 주장은 별도 검증이 필요하다.
- Historical 47.6%는 그대로 역사값이다. 같은 42개 라벨을 다시 심사해 생성 모델의
  성능이 바뀌었다고 주장하지 않는다.

실제 NVIDIA 3건(2026-11-16, `gpt-oss-20b`)에서:

| 저장 방식 | 저장된 근거 없는 효과 주장 |
| --- | ---: |
| Baseline (수치 가드레일만) | 4 |
| Variant (수치 + 효과 Gate) | 0 |

최종 수치와 두 번째 실행의 상세는
[`../evaluation/hallucination-experiments.md`](../evaluation/hallucination-experiments.md) 에 있다.

## 7. 검증하지 못한 가설

1. **검색 실패가 생성 실패보다 큰 비중을 차지한다** — 42개 중 12개가 문맥 내 근거로도
   막히지 않았으므로 이번 표본에서는 지지되지 않았다. 다만 실제 회사 저장소의 긴
   문서에서는 다를 수 있다.
2. **프롬프트만 강화하면 Gate 없이도 해결된다** — 프롬프트를 강화한 뒤에도 live 3건 중
   2건에서 근거 없는 효과 주장이 나왔다. 프롬프트는 필요하지만 충분하지 않다.
3. **Judge 모델이 제품 경로에서도 충분히 정확하다** — 이번 라운드에서 제품 경로에
   Judge 를 넣지 않았다. 비용·지연·오탐 위험을 측정하지 않았다.
4. **한국어 효과 표현 목록이 일반화된다** — 22개 효과 주장은 동결 데이터셋 기준이다.
   다른 도메인·문체에서의 재현율은 측정하지 않았다.
5. **다른 개발자의 기여를 AI가 잘못 귀속한다** — Historical c001 1건 외에 제품 경로의
   AI 기여 문장을 라벨링한 데이터가 없다.

## 8. 결론

- 직접 원인은 **F. 검증 실패**와 **G. 보고서 재유입**이다. 생성(D)이 효과 주장을
  만들지만, 저장·보고서 단계에 결정론적 검증이 없어 그대로 통과했다.
- 가장 작은 유효 변경은 "효과 주장을 문장 단위로 추출하고, 외부 근거와 대조해
  근거 없는 문장을 저장 전에 삭제하는 것"이었다.
- 검색·재정렬·Judge 제품화는 남은 8개 claim(기능 존재·의미 반대·귀속·용량)을 위해
  필요하지만, 이번 라운드에서는 효과 주장 12개를 먼저 막는 것이 비용 대비 효과가
  컸다.
