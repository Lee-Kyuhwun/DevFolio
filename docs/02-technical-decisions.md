# 기술적 의사결정 분석

기준일: 2026-11-15

이 문서는 **코드와 git 이력으로 확인되는 사실**과 **구조를 근거로 한 추론**, **추가 검증이 필요한 가설**을 구분한다. 당시 개발자의 실제 의도는 커밋 메시지·문서에 남아 있는 범위에서만 인정했다.

## 1. "문서"가 아니라 "데이터"를 원본으로 둔다

**[A]** 저장 모델(`Project`, `Task`, `Period`)과 렌더링(`TemplateEngine.render(projects, config, template_name, doc_type)`)이 분리되어 있다. 문서 종류를 바꾸면 같은 데이터에서 다른 산출물이 나온다.

**대안 비교**

| 대안 | 장점 | 이 프로젝트에서의 문제 |
|---|---|---|
| 문서 편집기(WYSIWYG) 중심 | 즉시 결과 확인 | 문서마다 내용이 갈라지는 원래 문제를 해결하지 못함 |
| DB + 웹 서비스 | 다중 기기, 협업 | 로컬 우선·무계정 원칙과 충돌, 운영 부담 |
| **구조화 파일 + 렌더링 (채택)** | 사람이 열어 고칠 수 있고, git으로 버전 관리 가능 | 동시성·부분 갱신을 직접 다뤄야 함 |

**[A]** 저장은 YAML 원자적 쓰기 + `0600` 권한이다. **[B]** "사용자가 자기 데이터를 직접 통제한다"는 원칙을 파일 포맷 선택으로 구현한 것으로 보인다.

**트레이드오프 [A]**: 파일 기반이라 다중 프로세스 동시 쓰기에 대한 잠금이 없다. 서버를 두 개 띄워 같은 프로젝트를 동시에 저장하면 마지막 쓰기가 이긴다. 현재 사용 규모(로컬 단일 사용자)에서는 수용 가능한 선택이다.

## 2. 웹 UI를 프레임워크 없이 만든 결정

**[A]** `package.json`, 번들러, node 의존성이 없다. `studio_v2.js`는 IIFE 하나이고 `root.innerHTML`을 매번 재구성한다.

**왜 이 선택이 합리적이었는가 [B]**
- Docker 이미지에 Node 빌드 단계가 필요 없다(`Dockerfile`은 python:3.12-slim 기반).
- 오프라인 로컬 도구이므로 CDN·번들 크기 최적화의 이득이 작다.
- 단일 파일이라 `StaticFiles`로 그대로 서빙된다.

**무엇을 지불했는가 [A]**
- 전역 `state` + 전체 재렌더 → 검색 입력 한 글자마다 DOM 전체 교체(이번에 수정).
- 포커스/스크롤/IME 조합 상태가 렌더에 의해 초기화될 수 있음.
- 접근성 속성(포커스 표시, 라이브 리전, 모달 시맨틱)을 직접 챙겨야 함 — 실제로 누락되어 있었다(05, 06 문서).
- JS 테스트가 없다. 회귀를 자동으로 잡을 수단이 브라우저 수동 확인뿐이다.

**대안 [C]**: Preact/htm 같은 3KB급 라이브러리는 빌드 없이도 쓸 수 있어 위 비용의 상당 부분을 줄인다. 다만 이번 작업에서는 **의존성 추가 없이** 같은 효과(부분 갱신)를 얻는 쪽을 택했다. 프레임워크 도입은 별도 판단 사안이다.

## 3. Pydantic을 "검증기"가 아니라 "경계"로 쓰기

**[A]** 세 겹의 검증이 있다.
1. 웹 요청 DTO (`ExperienceDraft`, `DraftPreviewRequest`)
2. 저장 직전 재검증 — `Project.model_validate()` (INC-16 조치)
3. 설정 파일 로드 시 `Config.model_validate()`

**[A]** INC-16의 원인은 `model_copy(update=...)`가 Pydantic 검증을 실행하지 않는다는 점이었다. 즉 "Pydantic을 쓰고 있다"는 사실만으로는 안전하지 않았고, **저장 직전 재검증**이라는 명시적 단계가 필요했다.

**[B]** 이 사례는 프레임워크 사용과 검증 보장이 별개라는 좋은 예다. 면접에서 설명 가치가 높다.

## 4. HTML 출력 보안: 허용 목록 + sandbox

**[A]** `ExportEngine._md_to_html_body()`는 문서용 태그·속성·URL scheme 허용 목록으로 변환하고, 미리보기 iframe은 `sandbox="allow-scripts"` + `title`을 갖는다. Mermaid는 strict 설정이다.

**[A]** INC-17 기록에 따르면 이전 구현은 사용자 입력의 `<script>`, `onerror`, `javascript:` 링크를 그대로 출력했고 iframe은 격리 없이 같은 출처에서 실행됐다. 즉 **XSS가 실제로 가능한 상태였다**.

**트레이드오프 [B]**: 허용 목록 방식은 표현력을 제한한다(임의 HTML 삽입 불가). 경력 문서라는 도메인에서는 합리적이다. 다만 허용 목록이 좁아 사용자가 원하는 마크업이 무시될 수 있고, 그 사실이 UI에 표시되지 않는다 **[C]**.

## 5. AI를 "신뢰하지 않는 부품"으로 다루기

**[A]** AI 경로에는 다음 방어가 코드로 존재한다.

| 방어 | 근거 |
|---|---|
| 빈 응답을 성공으로 보지 않음 | INC-05 |
| HTTP 200 본문의 거절 문구 감지 | INC-09 |
| 모델 404 시 다음 후보로 이동 | INC-02 |
| 할당량 0과 일일 한도 소진 구분 | INC-01 / INC-12 |
| 코드펜스·설명문 섞인 JSON 추출 | INC-03 |
| 한국어 문서의 외국어 문자 제거 | INC-04 |
| 심사 결과를 점수로 재검증 | INC-08 |
| 추론 모델의 thinking 토큰 여유 확보 | INC-11 |

**[A]** 각 항목에는 `test_incNN_*` 회귀 테스트가 있고, 문서에 "조치를 되돌리면 테스트가 실패하는지" 확인 결과가 적혀 있다.

**이 패턴의 의미 [B]**: 이 프로젝트의 AI 통합은 "프롬프트를 잘 쓰는" 접근이 아니라 **외부 모델을 신뢰할 수 없는 입출력 경계로 취급**하는 접근이다. 다만 INC-12가 보여주듯 방어가 과잉 판정으로 번질 수 있어, "고친 경우"와 "건드리면 안 되는 경우"를 모두 테스트로 고정하는 규율이 필요했다.

**한계 [A]**: 이 방어들은 모두 LLM 응답의 **형태**를 검사한다. 내용의 사실성은 검사하지 않는다. 경력 서술에서 사실 여부는 사람이 확인해야 한다.

## 6. 로컬 우선 + opt-in 동기화

**[A]** GitHub 동기화는 `sync.enabled`가 켜지고 `devfolio sync run`을 실행해야만 동작한다. 인증 정보는 keyring → 환경변수 → None 순서로 찾는다(`utils/security.py`).

**[B]** "기본은 아무것도 밖으로 나가지 않는다"를 코드 기본값으로 강제한 설계다. 웹 서버도 Swagger UI를 끄고(`docs_url=None`) 127.0.0.1 바인딩을 기본으로 한다.

**주의 [A]**: 웹 API에는 인증이 없다. 따라서 `--host 0.0.0.0`으로 띄우면 같은 네트워크의 누구나 데이터를 읽고 쓸 수 있다. README는 이 옵션을 안내하지만 경고는 없다 **[C] → 개선 필요**.

**[A]** `ai_logs.jsonl`에 provider/model/지연/문자 수/성공 여부를 기록하고, `/api/ai-logs`로 조회하는 Settings 탭이 있다.

**한계 [A]**: 파일은 무한히 커진다(회전 없음). `/api/ai-logs`는 파일 전체를 읽은 뒤 최근 N건만 반환한다. 이번에 `limit` 범위를 1~1000으로 고정했지만, 파일 크기 자체를 다루지는 않았다.

## 10. AI 신뢰성: LiteLLM Router 도입 대신 단일 제어 지점 유지

**[A]** litellm `Router`는 `num_retries`·`retry_policy`(오류 유형별 재시도 횟수)·`allowed_fails`/`cooldown_time`(배포 차단)·`fallbacks`를 제공한다. 2026-11-15 문서 기준으로 4xx 중 401/403/408/409/429를 제외한 응답과 not-found는 재시도하지 않는 것이 기본 정책이다.

**대안 비교**

| 대안 | 장점 | 이 프로젝트에서의 문제 |
|---|---|---|
| litellm `Router` 전면 도입 | 재시도·차단·폴백을 검증된 코드로 해결 | Provider 설정·키 주입 경로를 전면 교체해야 함. 기존 293개 테스트가 고정한 호출 경로가 깨질 위험이 큼 |
| 별도 AI Gateway 프로세스 | 언어·팀 무관 재사용 | 로컬 단일 사용자 도구에 프로세스를 하나 더 띄우는 비용이 이득보다 큼 |
| **현행 호출 지점에 정책만 이식 (채택)** | 기존 경로·테스트 유지, 변경 범위 국소 | 정책을 직접 유지보수해야 함 |

**[A]** 채택한 구현은 Router의 정책 시맨틱을 그대로 따른다 — 재시도 금지 목록, 지수 백오프, Cooldown 차단, `max_retries=0`으로 중첩 재시도 제거.

**트레이드오프 [A]**: Provider `/v1/models` 자동 동기화는 아직 없다. 모델 목록은 정적 레지스트리이며 폐기 시 수동 갱신이 필요하다. 대신 폐기 모델은 첫 실패에서 영구 차단되어 반복 호출 비용이 없다.

## 11. 확인이 필요한 가설

| 가설 | 왜 아직 가설인가 | 검증 방법 |
|---|---|---|
| 화면별 부분 렌더로 전환하면 체감 속도가 좋아진다 | 체감 지표를 측정하지 않았다 | INP/Long Task 측정, 렌더 횟수 계측 |
| 표시 템플릿이 많아지면 `doc_type × template` 조합 검증이 필요하다 | 현재 조합이 3×3 이하 | 조합별 렌더 스냅샷 테스트 |
| `--host 0.0.0.0` 사용자에게 경고가 필요하다 | 실제 사용 빈도를 모른다 | 실행 로그/이슈 확인 |
| AI 로그 회전이 필요하다 | 로그 크기 분포를 모른다 | 실제 `ai_logs.jsonl` 크기 측정 |
