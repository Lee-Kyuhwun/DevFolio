# 성과노트 기술적 의사결정

기준일: 2026-11-15, 버전 1.0.0

표기: **[A] 사실**(코드·테스트로 확인) · **[B] 추론**(구조 근거) · **[C] 가설**(추가 검증 필요)

---

## 1. 기록과 해석을 분리한다 — Activity / Achievement / AIAnalysis

**[A]** `Activity`(사실) → `Achievement`(해석) → `AIAnalysis`(제안)가 각각 별도 모델·컬렉션이다.
AI 결과는 `analyses.json` 에 저장되고, 사용자가 "성과 후보로 저장"을 눌러야 Achievement 가 된다.

**대안**: 메모 한 건이 곧 성과가 되는 단일 모델.

**선택 이유**: 평가 시즌의 문제는 "기록이 없다"와 "근거 없이 해석한다"가 섞여 있다.
원본 기록을 불변으로 두면 AI 실패·재분석·수동 수정이 서로를 덮어쓰지 않는다.

**비용**: 화면에 기록/성과/AI 세 단계가 생기고, 사용자가 묶는 행동을 한 번 더 해야 한다.

---

## 2. YAML 대신 컬렉션별 JSON 저장

**[A]** `core/store.py` 의 `JsonStore` 가 `activities.json` 등 컬렉션 단위로 저장한다.
임시 파일 + `os.replace` 로 원자적으로 쓰고 권한을 `0600` 으로 맞춘다.

**대안**: 기존 DevFolio 처럼 프로젝트별 YAML(ruamel, 주석 보존).

**선택 이유**: 성과노트의 핵심은 "빠른 기록"이라 파일 하나를 열어 편집하는 단위가 아니라
컬렉션 단위 CRUD 가 맞다. Pydantic 모델 변경을 기본값으로 흡수하기도 쉽다.

**비용**: 사람이 직접 파일을 읽고 고치기는 YAML 보다 불편하다. 레거시 YAML 은 읽기 전용으로만 다룬다.

---

## 3. 수치 가드레일을 서비스 경계에 둔다

**[A]** `core/metrics.py` 의 `find_claims`, `unsupported_claims`, `sanitize_claims` 를
AI 결과(`sanitize_ai_result`)와 보고서(`build_content`) 양쪽에서 호출한다.

**대안**: 프롬프트로 "숫자를 만들지 마세요"라고 지시.

**선택 이유**: 프롬프트는 확률적이다. 모델이 만든 `40%` 가 문서에 들어가는 것을 막으려면
결정론적 후처리가 필요하다. 검증되지 않은 수치는 `[확인 필요]` 로 치환하고 부록에 남긴다.

**비용**: 정당한 수치도 원본 텍스트에 없으면 본문에서 빠진다(현재 가장 큰 UX 마찰).

---

## 4. AI는 동의 게이트 뒤에 두고, 신뢰성 계층은 재사용한다

**[A]** `impactnote/core/ai.py` 가 `Settings.external_ai_consent` 와 `allowed_providers` 를 확인한 뒤
`devfolio/core/ai_service.AIService._call()` 을 호출한다. 재시도·모델 차단·오류 분류는
기존 `ai_reliability` 를 그대로 쓴다.

**대안**: 새 AI 클라이언트를 처음부터 구현.

**선택 이유**: 회사 업무 데이터는 민감하다. 기본 차단 + 명시 동의가 필요하고,
Provider 장애 대응은 이미 23개 장애 기록으로 다듬어진 계층을 재사용하는 편이 안전하다.

**비용**: 레거시 모듈에 대한 의존이 남고, Provider별 정책 변경은 공통 계층에서 관리해야 한다.

---

## 5. Git 후보는 AI 없이 결정론적으로 만든다

**[A]** `suggest_from_git()` 은 커밋 제목·변경량을 규칙으로 분류해 Activity 와 후보 Achievement 를 만든다.
항상 `needs_review` 이며 `confirmed` 전에는 `verified` 가 될 수 없다.

**대안**: 커밋 로그를 LLM 에 넣어 성과 문장 생성.

**선택 이유**: Git 이력은 양이 많고 민감하다. 외부 전송 없이도 "무슨 일을 했는지" 후보를 만들 수 있고,
AI 를 쓰더라도 사용자가 명시적으로 선택하게 하는 편이 비용·프라이버시 면에서 낫다.

---

## 6. 보고서는 템플릿 + 검증 지표 + 확인 필요 부록

**[A]** `report.py` 가 템플릿 A~E 의 섹션을 조립하고, `Metric.verified` 인 것만 본문에 쓰며,
미확인 수치·상태는 "근거 및 확인 상태" 부록에 모은다. 같은 기간·템플릿은 버전을 올린다.

**대안**: 자유 양식 편집기.

**선택 이유**: 제출 문서는 양식이 정해져 있고, "무엇이 빠졌는지"를 보여주는 것이 신뢰를 만든다.
버전은 재생성 이력을 남겨 어떤 내용을 냈는지 추적하게 한다.

**비용**: 회사별 세부 양식 커스터마이징은 아직 제한적이다.

---

## 7. DevFolio 이전은 백업 + 멱등 + 원본 불변

**[A]** `migrate.py` 가 레거시 data/config 를 ZIP 으로 백업하고, `source_ref=legacy:<project>:<task>` 로
중복을 막고, `migration.json` 지문으로 재실행을 감지한다. `IMPACTNOTE_LEGACY_DATA_DIR` 우선으로 읽는다.

**대안**: 기존 데이터를 그 자리에서 변환.

**선택 이유**: 되돌릴 수 없는 삭제·변형은 금지 원칙에 어긋난다. 사용자가 이전을 후회해도 원본은 남는다.

**비용**: 데이터가 두 곳에 존재하는 기간이 생기고, 이후 변경은 자동 동기화되지 않는다.

---

## 8. 새 제품을 새 패키지로 두고 레거시는 호환 계층으로 유지

**[A]** `impactnote/` 신설, `devfolio/` 는 CLI·API·YAML·export_engine·ai_service 제공.
`pyproject.toml` 은 두 패키지를 모두 포함하고 `impactnote`/`devfolio` 두 진입점을 노출한다.

**대안**: `devfolio/` 를 전면 재작성.

**선택 이유**: 401개 레거시 테스트와 사용자 데이터를 보존하면서 제품을 전환할 수 있다.
내보내기·AI 신뢰성 자산을 다시 구현하지 않아도 된다.

**비용**: 두 패키지가 공존해 구조가 커지고, 문서에서 "현재/레거시"를 구분해야 한다.

---

## 9. 프론트엔드는 프레임워크 없이 SPA

**[A]** `index.html` + `app.js`(상태 객체 + 렌더 함수) + `app.css`. 빌드 단계 없음.

**대안**: React/Vue + 번들러.

**선택 이유**: 화면 8개·폼 중심 UI 에 빌드 파이프라인은 과하다. Python 패키지에 정적 파일로 포함해
Docker 이미지 하나로 배포할 수 있다.

**비용**: 화면이 늘어나면 수동 렌더링과 이벤트 위임이 복잡해진다. 실제로 폼 제출에서
`FormData` 대신 form 요소를 넘기는 버그가 브라우저 검증에서 발견됐다.

---

## 10. 검증은 "테스트 통과"가 아니라 "실제로 막는가"로 확인

**[A]** 이번 전환에서 다음을 실행했다: pytest 431, ruff, `node --check`, Docker 빌드·기동,
컨테이너 내부 E2E, 마이그레이션 2회 실행·원본 해시 비교, 브라우저 기록→성과→보고서 흐름.

**선택 이유**: 과거 INC-07("검증 장치가 아무것도 막지 않음")의 교훈이다.
테스트가 있어도 실제 경로가 깨져 있으면 의미가 없다.

**결과**: 브라우저 폼 버그, 좁은 화면 레이아웃, Docker 마운트 경로 마이그레이션, CI lint 누락을
실행 중에 발견해 수정했다(`docs/agent-incidents.md` INC-25).
